# Four-day solo P0 — Grok / Codex writes the code

This is a **solo** build with a **four-day** deadline. All application code is generated by **Grok or Codex**. The human owns feed access, gate calls, demo recording, and honest claims. The 14-day four-person deck (slide 22) and the 5–7 week solo deck (slide 25) are both too slow.

The original Day 1–3 critical path is still the right sequence. Compress it into the first two days. Do not simulate four parallel people. Sequence the four workstreams and let the model generate each module.

**Submission story**

> We onboard heterogeneous government feeds into a vendor-neutral registry, continuously generate reviewable ANPR sightings, correlate them with an authorised watchlist, and show timestamped evidence and observed movement on GIS, while retaining existing departmental recording infrastructure.

The decisive Day-1 question is **feed access**, not model selection.

---

## How solo + AI actually works

| Role | Does | Does not |
|---|---|---|
| Human | Portal login, RTSP/ONVIF credentials, run the host, hit the gates, record demos, refuse fake coverage numbers | Hand-write the app |
| Grok / Codex | All code: schema, APIs, ingest, ANPR worker, matching, GIS UI, seed data, reports | Invent government-feed access or measured GPU capacity |

Workstreams are **serial for one person**, generated as complete modules:

1. **C — backend** — event schema, SQLite/Postgres, registry, watchlist, exact match, audit
2. **B — ANPR** — file/RTSP ingest, plate crop, candidate OCR, independent multi-frame vote, evidence
3. **D — UI/GIS** — ledger, alert queue, evidence, inferred path. Stop if there is no Day-1 sighting
4. **A — coverage** — 50-camera ledger, health vs analytics_active, government-feed adapter

Prompt the model with this file and `AGENTS.md` every session. Do not ask it for Kafka, Kubernetes, faces, or a statewide VMS.

## Day-by-day (solo)

### Day 1 morning — access + schema

- Decode an authorised government feed on **this** host (GTX 1650). If the portal is closed, escalate and continue on own-feed frames.
- Freeze camera / sighting / watchlist / alert / evidence schema.
- Seed the 50-camera ledger (connected, blocked, or deferred — with reason).
- Grok/Codex: generate the FastAPI app, database, and seed scripts.

### Day 1 afternoon — first persistent sighting

- Own-feed: generated Indian plate frames **or** a labelled recorded clip.
- Worker must persist raw OCR + crop + camera + timestamp. Not a hardcoded UI string.
- Minimal map point only if that row exists in the database.

If there is no readable persistent sighting by end of Day 1, stop UI work.

### Day 2 morning — end-to-end alert

- Exact watchlist match → alert + evidence crop + GIS point on the same record.
- Two source types (file frames + RTSP or a second file) are useful. They do not replace the ~50-camera ledger.

If no real alert by midday, strip fuzzy / ByteTrack / relay / bonus.

### Day 2 afternoon — expand

- Keep adding accessible cameras to the ledger.
- Calibrate sampling from dwell time and passage recall. **Do not hard-code 2 FPS.**
- Exact-match only unless the midday gate passed.

### Day 3 — concurrency and honesty

- Run the worker on every camera that actually decodes.
- Show `analytics_active_count` / `onboarded_count` in the UI.
- If the 1650 cannot hold required FPS, drop sampling and say so.

### Day 4 — freeze, record, pack

- Midday feature freeze.
- Record own-feed (2–3 min) and government-feed (or an honest blocked-access clip + ledger).
- Output report: plate, camera, timestamp, crop, confidence, model hash, run ID.
- HLD + solution PPT. Claims must match the running app.
